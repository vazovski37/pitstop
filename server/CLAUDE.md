# server/ — log, validator, AI repair

Owner: **Vazovski** (since 18 October 2026, every folder is; `server/semantic/` was going to be the teammate's and does not exist).

## What this folder does
The single source of truth: the write-ahead log, the commit API, the WebSocket stream, the commit validator, AI repair and the type-check gate. Structural merge (jj + Mergiraf) happens in the daemon (`daemon/src/jj.ts`), never here: a write-write conflict is `rejected constraint_failed` and the daemon rebases. Design reference: the technical design doc (written when the project was called Agent Git), sections 4 to 7 and 11.

## Rules
- Every message in or out matches a schema in `@pitstop/protocol`. Validate input with `CommitRequest.parse(...)` etc. Never invent a field locally.
- The log is append-only. No `update` or `delete` on `changesets`, `changeset_files` or `changeset_symbols`.
- Assign LSNs inside one Postgres transaction. `PgStore.append` takes `pg_advisory_xact_lock` and uses `max(lsn) + 1`, so two concurrent commits never get the same LSN or skip one. Keep every append on that path.
- Schema changes go in a new `migrations/NNN_name.sql`. Never edit an applied migration.
- `buildApp()` in `src/app.ts` takes its dependencies as arguments so tests use `app.inject()` with fakes. Keep it that way.
- Never deploy from a laptop. Pushing to `main` deploys through GitHub Actions.

## Repositories
One server, many repositories (`repos` table, migration 003). LSNs count per repository and every log table is keyed by `(repo, lsn)`; `PgStore.append` locks per repository. A request without `repo` means `local/default`; an unknown repository is `invalid_request` (`POST /repos` first). A stream socket follows one repository from its `subscribe` on and is answered with `head` before any entry. `GET /repos`, `GET /repos/:owner/:name`, `GET /log?repo=`.

## Mirror
`src/mirror.ts` with `src/github.ts`: when `MIRROR_GITHUB_TOKEN` is set, every accepted entry of a repository with a mirror (`PUT /repos/:owner/:name/mirror`, table `repo_mirrors`) becomes a commit on its GitHub branch through the Git Data API, no git binary and no clone. Commits use the daemon's recipe (`daemon/src/jj.ts`, `buildCommit`: author `agent <developer@pitstop.local>`, committer `pitstop daemon`, both dates `createdAt`, message `#lsn intent`), so every laptop and GitHub name the same commit; the worker warns when GitHub's id differs. One worker per repository, in LSN order, position in Postgres; a push that is not a fast-forward marks the mirror `diverged` until a new `PUT`. The mirror is an export, never the truth.

## Access
`src/auth.ts`. Three identities: the shared `PITSTOP_TOKEN` (the administrator, super-user over every repository), a personal token `pst_…` (a user; `author.developer` becomes their login), or a session cookie from sign in with GitHub (`GET /auth/github`, needs `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`, `SESSION_SECRET`; in GitHub Actions they are `PITSTOP_OAUTH_CLIENT_ID` / `PITSTOP_OAUTH_CLIENT_SECRET`, since GitHub refuses names starting with `GITHUB_`). A server with neither a shared token nor accounts is open; in production (`NODE_ENV=production`) it refuses to start that way. With accounts, `repo_members` (migration 005) decide: commits and intents need writer or owner; the log, the stream and `GET /repos/:o/:n` need reader or a public repository; a repository with **no members is closed to users** (only the administrator, who adds its owner). A user creates repositories only under their own login (`<login>/<name>`, lowercased) and becomes owner; `POST /repos` on an existing id answers it to whoever may read it and `409 taken` to anyone else. Owners manage members; a member may remove themselves; nobody may remove or demote the last owner. Mirrors are the administrator’s alone (one server-wide GitHub token pushes them). Tokens go in `Authorization: Bearer`; `?token=` is accepted only on `/stream`, where a browser cannot set headers, and the request logger drops query strings. A cookie-identified `/stream` upgrade must come from this server’s own origin (cross-site WebSocket hijacking). A `subscribe` to a repository that does not exist and to one the socket may not read are refused alike (close 1008, one message), as the HTTP API answers both with 404, so nobody learns which private names exist. Routes: `/me`, `/tokens`, `/repos/:o/:n/members/:login`, `PATCH /repos/:o/:n {visibility}`.

## Validation
`src/validate.ts` runs inside `Store.append`, under the append lock, against the entries after the commit's base (writes from `baseLsn`, reads from `readBaseLsn`). Write-write on a file or symbol: `rejected constraint_failed` with `conflictsWith`; the daemon rebases and retries. Write skew (a read symbol changed in the gap): `PITSTOP_VALIDATE=warn` (default) lands it with the skew in `checks.details` and a `warning` on the stream, `enforce` answers `rejected repair_failed`, `off` skips the validator. With a resolver (`PITSTOP_REPAIR`), the validator only reports skew: `agent` answers `rejected escalated` with what changed, and the coding agent that committed fixes its change and commits again; `groq` (`src/repair.ts`, `src/groq.ts`) asks Groq Cloud for a patch to the commit's own files, type-checks it against `treeAt(head)`, retries once with the errors, and escalates after two failures. A repaired entry lands with the patched files and a `repairs` row, so every worktree receives the fixed version. The repair runs inside the append lock, so a model call holds other commits for a few seconds.

## A member decides on write skew
In `agent` mode a repository with members does not bounce write skew back to the committing agent: the commit is **parked** (`parked_commits`, migration 007, written after the append rolled back so the lock is free) for its **deciders**, the members marked `resolver` (migration 006), else its owners. The committer gets `rejected escalated` saying who decides and the parked id, and a `warning` goes on the stream; the same author's next commit is refused (`constraint_failed`) while it waits, so the change cannot slip past by being committed again. A decider (or the administrator) answers on the website: `POST /repos/:o/:n/parked/:id/accept` lands it as it is (write-write still checked) with `checks.details` and a `repairs` row naming them; `.../send-back {note}` closes it and warns the author, whose agent adapts and commits again. When the committer is the only decider, or the repository has no members (the shared token made it; the gates), the plain escalation applies. `GET /repos/:o/:n/parked` lists them, open first.

## Early warnings
`POST /intents` compares the new intent's `declaredSymbols` with the repository's open intents (`Store.openIntents`) and broadcasts one `warning` of kind `overlapping_intent` to each side (`validate.ts`, `overlapWarnings`). Only open intents count: the brain's sweep (below) marks quiet ones stale. `similar_symbol` (semantic reuse) is not built; vectors are gone (migration 008).

## Brain
The design doc's section 9 and the query API of section 10, per repository (migration 009: `repo_adrs`, `repo_brain_versions`, `repo_leases`; 001's global `adrs`, `leases`, `brain_versions` stay unused). `src/brain.ts` holds the commit-path check, the routes and the sweep; `src/adr-rules.ts` is the pure rule engine; `src/review.ts` the advisory model review. Both stores implement it, and `src/test-support.ts` runs one suite against both.
- **ADRs and rules (9.1).** An ADR is a decision with its reason and consequences, which every agent receives when it declares an intent (the daemon reads `GET /repos/:o/:n/brain`), plus rules (`AdrRule` in the protocol). A writer proposes (`POST /repos/:o/:n/adrs`; `ruleProblem` checks each rule: globs up to 200 characters with balanced braces, a `forbid_pattern` up to 200 that V8's linear-time engine can run (no backreferences, no lookahead, no large counted repeats), `call` up to 100, `message` 500, `question` 1,000); owners and the administrator decide (`POST …/adrs/:n/accept|reject|supersede`). **No user-written expression can stall the event loop**: patterns and globs compile with the `l` flag (`linearRegExp`); `adr-rules.ts` turns `--enable-experimental-regexp-engine` on at load and the Dockerfile starts node with it, and a test asserts `LINEAR`. Globs: `**`, `*`, `?`, `{a,b}`, a trailing `/` (everything under it); the same source runs in Postgres (`~`). Mechanical rules: `forbid_import` (imports, exports from, `import()`, `require()`, not inside strings, `import type` skipped; relative specifiers resolved to repository paths, trying `.ts`, `.tsx`, `.js`, `/index.ts`; `./x.js` means `./x.ts`; aliases from the root `tsconfig.json`'s `paths` and `baseUrl`, and `@/`, `~/` for `src/` when it has none; a bare target is a package name), `forbid_call` (`foo(` or `obj.method(`, not in comments, strings or regex literals, not a method definition or signature such as `query() {` or `query(): T;`), both on code files only (`.[cm]?[jt]sx?`, `.vue`, `.svelte`); `forbid_pattern` on any file, line by line (CRLF too). The commit path (`checkCommit`, before the append, outside the lock) runs them on the files a commit adds or modifies with content; a violation the file already had at the commit's base (same ADR, rule, detail and line text, counted) is not the commit's: it goes into `checks.details` as "pre-existing, on the re-check queue" and never blocks an edit to a legacy file. A violation the commit brings is `rejected constraint_failed` (inside the append): per ADR, each `file:line` and the rule, then "Do instead:" and the ADR's decision, and how many older ones were already there. A rename without content into a rule's scope is `invalid_request`. `checks.adr` is `pass` when a rule applied and held, `skipped` when none applied. `ai_review` rules in scope are asked of a model (`AppDeps.reviewer`, Groq when `GROQ_API_KEY` is set) only when the mechanical rules hold, before the append, outside the lock, with a 20 s timeout; the answer goes into `checks.details` as advice and never refuses; without a model the rule is noted as not run. A rule that cannot run is noted, never fatal.
- **Versioning and re-check (9.2).** A repository's brain version starts at 0 and moves by one with each accept or supersede (one `repo_brain_versions` row each, in the same transaction as the status change and the stamp on the moved ADR, under a per-repository advisory lock); rejecting a proposal changes no rule and moves nothing. The commit path and the brain routes read the version from the ADR list itself (`brainVersionOf`: the highest stamp), so a commit's rules and its recorded version come from one snapshot. Every status change, a proposal included, is broadcast as a `brain` message with the version after it. A changeset records the version it was validated against (`Decision.brainVersion`, else the current one). `GET /repos/:o/:n/brain/at?lsn=` (or `?version=`) answers what the rules said then: the ADRs whose last move at or below that version accepted them. `GET /repos/:o/:n/brain/recheck` (writers only) runs the accepted mechanical rules over the files at head their globs cover (`Store.filesAt`; `pathsAt` for exact import resolution), outside any lock, remembered per (repository, head, version), and answers the current violations and the re-check queue: landed entries, oldest first, that touched an offending file and were validated under a brain version older than the ADR they now break. No accepted mechanical rule: it reads nothing.
- **Leases (9.4).** `POST /repos/:o/:n/leases {symbol, agent, developer?, reason?, ttlSeconds?, intentId?}` (writer; a signed-in user is the developer; 60 to 1800 s, default 300): one transaction that first takes the repository's append lock (so a grant waits for a commit in flight), expires a held lease past its expiry on that symbol, then `insert … on conflict do nothing` against the partial unique index on `(repo, symbol) where status = 'held'`, so exactly one holder wins; anyone else gets 409 with the holder. The holder is the intent (`holdsLease`): a lease taken for an intent is that intent's, so the same person's other checkout (same developer and agent name) is refused like anyone else; an intent must be the holder's own. Its holder renews it by asking again (the daemon does, on a timer, while the intent is open); **`Store.heartbeat` renews nothing**, since any reader of the stream may send a heartbeat naming any intent. A commit that closes the intent releases its leases (broadcast: the intent, committed, and each `lease`); only the intent's own author closes it. While it is held, another commit writing the symbol (its write or signature write set; with no symbol sets at all, any change to the symbol's file) is `rejected constraint_failed` naming the holder, the intent and the expiry; the check runs inside the append on leases read through the append's own connection (`Decide`'s `AppendReads`), so a lease granted while a commit waited on a model review or the lock still refuses it. `DELETE /repos/:o/:n/leases?symbol=&agent=&developer=&intentId=`: the holder (a daemon names its agent and developer, every agent may be called `claude-code`; anyone else gets 403), an owner or the administrator; only the lease checked is released, never one taken since. `GET …/leases` lists the live ones.
- **Stale intents (9.3).** A sweep in `buildApp` (every 30 s, `sweepMs`, started on `onReady`, stopped on `onClose`, `app.brainSweep()` for tests; the clock is `AppDeps.now`) marks open intents with no heartbeat for five minutes (`staleAfterMs`) stale, broadcasts them and releases their leases, then expires leases past `expires_at` and broadcasts those. A crashed agent blocks nobody for long. A commit still closes a stale intent; a heartbeat does not reopen it.
- **Query API (10).** `GET /repos/:o/:n/symbols?prefix=` (each symbol the log saw written, with its last writer entry, intent, agent, whether that entry changed its signature, and its live lease); `GET …/symbols/:id/history` (every entry that wrote it, newest first, with intents, plus who has it declared or leased now); `GET …/symbols/:id/callers` (entries whose read set holds it, with the symbols they wrote; the answer says it is derived from read sets, not a parsed call graph); `GET …/why?path=` (entries that touched the path or renamed from it, newest first, with intents, repairs and brain versions); the three take `?before=<lsn>` for the next page; `touches` (a path glob, checked like a rule's) and `since` on `GET /log`. Symbol ids hold `/` and `#`, so they come URL-encoded (Fastify's `maxParamLength` is 2,048 for them). The same two answer with the symbol in the query string, `GET …/history?symbol=` and `GET …/callers?symbol=`, and the daemon uses those: Azure Container Apps' ingress rewrites an encoded `/` in a path, so the path form never reaches the hosted server. None of these reads a blob: `LogQuery.contents` is off unless asked (`/log?touches=` asks). All through `access`: a repository the caller may not read is a 404.
- The plain escalation path (agent mode, no deciders, or Groq giving up) broadcasts a `warning` of kind `dependency_changed` too, as the parked path does, so the live view sees it.

## Checks
`src/checks.ts` runs `tsc --noEmit` on `Store.treeAt(head)` plus the commit's files, in a temp folder, with the server's own TypeScript (a dependency, so the image has it). The tree must carry its own `tsconfig.json` and need nothing from `node_modules`: the demo slice does, the pitstop repo itself does not. `PITSTOP_CHECK=always` gates every commit (a failure is `rejected constraint_failed` with tsc's errors); `off` (default) leaves it to the repair path. `treeAt` needs the repository to have entered the log as a full import at its first entry.

## Live view
`web/` (its own `CLAUDE.md`) is a static page the server serves at `/` with `@fastify/static` when `buildApp` gets `webDir`; `index.ts` takes `PITSTOP_WEB_DIR` or `web/dist` next to the server, and the Dockerfile builds it into the image. The files are open routes (`/*`): on a shared-token server the page asks for the token itself and sends it on every request. API routes are registered before the static wildcard, so they win. `GET /repos/:owner/:name/worktrees` (reader access) answers what each connected daemon heartbeated on its socket, `appliedLsn` and the open `intentId`, with the intent's agent as the name and the head to compare against; the stream keeps that per socket (`Stream.worktrees`), so it lives on the one replica like the subscribers.

## Presence
The brain's live part (design doc 9.5): which agents are working, on what, in which files and symbols. A CRDT, the last-writer-wins map in `packages/protocol/src/presence.ts`, and never used for decisions. `src/presence.ts` (`PresenceDocs`) holds one document per repository in memory, like the subscribers. `stream.ts`: a `presence` client message from a socket that subscribed is merged with `applyPresence` when its repository is the socket's (else ignored) and the socket may **write** it (`connect`'s `options.canWrite`; absent, the socket writes no presence at all): what presence says (intent text, files) reaches the members' coding agents as safe-point notes, so reading a repository, public ones included, is never enough. One socket writes at most 4 replicas (`PRESENCE_REPLICAS_PER_SOCKET`; a daemon writes one). A signed-in user's entries are written as their login (`options.developer`), and a replica is bound to the writer who last wrote it (a login, or `shared`): another writer's entry for it is refused while it is live (not departed, within the TTL). A stamp of another replica, more than a minute ahead of this clock, or an entry over 64 KB is refused; refusals are logged once per socket. A merge that changed the document goes to every socket following the repository as `presence {repo, entries: [entry]}`. After `subscribe`, once `head` and the open intents are out, the whole document (tombstones included) if it is not empty. A socket that closes leaves a tombstone for each replica it wrote, stamped just after that replica's last stamp, unless someone wrote the replica since (a reconnect); the departure runs after the messages the socket already sent, so a presence still being handled lands first and the tombstone follows it. At most 500 entries and 1 MB of JSON per repository (oldest tombstones dropped first, then the oldest entries), and entries an hour old are forgotten; views hide entries older than two minutes (`PRESENCE_TTL_MS`), so daemons refresh theirs with every heartbeat. Messages from one socket are handled in order, so a `presence` right after `subscribe` finds the repository set. The `/stream` route in `app.ts` passes the signed-in user as `developer` and writer access as `canWrite`.

## Known constraint
The stream keeps subscribers in memory, so the Container App runs exactly one replica (`infra/main.bicep`). To scale out later, fan new entries out through Postgres `LISTEN/NOTIFY`.

## Commands
- `npm run db:up` (repo root): local Postgres (the pgvector image; nothing uses the extension after migration 008).
- `npm run dev -w @pitstop/server`: server with reload, reads `../.env`.
- `PITSTOP_STORE=memory npm run dev -w @pitstop/server`: the same without Postgres (nothing persisted); enough for daemon work.
- `npm test` (repo root): unit tests; migration tests run when `DATABASE_URL` is set.
