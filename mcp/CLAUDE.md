# mcp/ — agent integration

Owner: **Vazovski** (since 18 October 2026; built by the teammate through Phase 4).

## What this folder does
Connects coding agents (Claude Code for the hackathon) to the daemon: MCP tools the agent calls, and the hook that marks safe points. Design reference: the technical design doc (written when the project was called Agent Git), sections 8.3, 10 and 13.

## Pieces
- `src/index.ts`: the MCP server over stdio. Tools `declare_intent` (its answer carries the brain in brief: version, accepted ADRs with their rules, leases others hold on the declared symbols), `commit`, `brain`, `lease`, `history`, `why`, `callers`, `status`, `who`. There is no `similar`: vectors were dropped on 18 October 2026. Its `instructions` (`INSTRUCTIONS`) carry the house rules, the same as the `CLAUDE.local.md` `pitstop setup` writes (daemon/src/wire.ts): declare an intent, commit only with the commit tool, never git commit/push, obey a refusal, follow the ADRs, leave leased symbols alone. The worktree is `PITSTOP_WORKTREE`, else the nearest directory with `.pitstop/config.json` at or above the current one (so `.mcp.json` needs no path). `startServer()` is what runs it.
- `src/tools.ts`: each tool as a plain function returning the text the agent sees (tested without the transport). `src/client.ts`: finds the worktree's daemon through `.pitstop/daemon.json` and calls its local API. The brain's text (one line per ADR, lease, intent) is formatted by the daemon (`daemon/src/brain.ts`), so the CLI and the tools say the same; `why`, `callers` and `history` come from the server's query API through the daemon. A refusal reaches the agent through `commit` as `refusal()` words it: `Commit rejected (<reason>): ` once (a daemon older than 0.1.6 sends its CLI line as the message; the prefix is taken off), the server's message, the entries it conflicts with, and advice only where the server gives none (a write-write conflict: Pitstop applies the entries by the next tool call, do not rebase yourself; a failed type check). A held or bounced-back write skew, a commit waiting for its resolver, and ADR and lease refusals carry their own instructions; a generic "commit again" would contradict the first two. `tools.test.ts` drives the tool through the real daemon (`daemon/src`, imported by path) against its fake server, with the server's refusal texts.
- `src/who.ts`: the `who` tool (presence, design doc 9.5), registered with one line in `index.ts`: who else is working in the repository right now, from the daemon's `GET /presence` (the live entries of the repository's presence CRDT, daemon/src/presence.ts). One line per other worktree: agent, developer, working or idle, intent, how fresh, applied LSN; then its files (the ones this worktree is in too marked) and symbols. A heads-up, never a lock; the overlap itself also reaches the agent once as a safe-point note.
- `src/hook.ts`: the Claude Code `PostToolUse` hook. It posts a safe point to the daemon, which applies pending entries then, and returns the daemon's notes (entries that touched the agent's work, conflicts, warnings) as `additionalContext`. Without a daemon it starts one (below), and on any failure it prints nothing and exits 0. `runHook()` is what runs it.
- `src/autostart.ts`: when no daemon answers (daemon.json missing, its pid dead, or `/status` not that pid) in a Pitstop checkout, run `pitstop start` there, detached, its output appended to `.pitstop/daemon.log`, then wait for the daemon. The server does it at startup (in the background) and when a tool finds no daemon (then tries the tool once more); the hook waits 3 s at most. A start that brought nothing up is not retried for 30 s (`.pitstop/autostart`), so a broken setup costs a tool call nothing. The CLI is `pitstop.js` next to the bundle, else this repository's daemon (`src/index.ts` under tsx, `dist/index.js` otherwise).
- `src/setup.ts`: `pitstop-agent-setup <worktree>` writes the MCP server into the worktree's `.mcp.json` and the hook and `mcp__pitstop` in `permissions.allow` into `.claude/settings.local.json` (Claude Code's per-user file, never the team's `settings.json`; Pitstop's hook is taken out of `settings.json`, where an earlier version put it) with absolute paths to this build, keeping whatever else is there. Hooks are filtered one by one, not by group: only `pitstop-hook` and `node "<abs>/mcp/dist/hook.js"` are Pitstop's. `pitstop setup` (daemon/src/wire.ts) writes them by command name instead, and each replaces the other's entries.
- `src/build-info.ts`: `BUNDLED`, true inside packages/cli's bundle, where the isMain checks of `index.ts` and `hook.ts` are off and the bundle's entries call `startServer`/`runHook`.

For a team that is not us: [daemon/README.md](../daemon/README.md) walks through the install from the server, `pitstop setup`, and the by-hand path.

## The bundle
`packages/cli/` bundles `startServer` as `pitstop-mcp` and `runHook` as `pitstop-hook`, next to `pitstop`; `pitstop setup` wires them into a checkout. On Windows `.mcp.json` says `cmd /c pitstop-mcp` (with `NoDefaultCurrentDirectoryInExePath=1`, so cmd never runs a `pitstop-mcp.cmd` from the checkout), because Claude Code starts an MCP server without a shell and npm's bin there is a `.cmd` shim; the hook runs through a shell, so plain `pitstop-hook` works everywhere. `pitstop start`, which autostart runs, gives the daemon the checkout's `.pitstop/config.json` over Claude Code's environment.

## Setup from source, per laptop and worktree
1. From the pitstop repo, once: `npm run build` (the daemon's and this package's `dist/`).
2. In the worktree the agent will edit (for the demo, the slice from `demo/scripts/reset.sh`): `node <pitstop>/mcp/dist/setup.js .` Then check `.mcp.json` and `.claude/settings.local.json` in that worktree.
3. Start the daemon there (after `pitstop init`, which writes `.pitstop/config.json`; without it `daemon` refuses): `node <pitstop>/daemon/dist/index.js daemon` with `PITSTOP_SERVER`, `PITSTOP_TOKEN`, `PITSTOP_AGENT` and, for the shared token, `PITSTOP_DEVELOPER` set (a personal token's owner is asked of the server) (the demo's `agent-a` / `agent-b`). It prints the local API port and writes `.pitstop/daemon.json`.
4. Open Claude Code in the worktree. The `pitstop` tools appear; after every tool call the hook runs and the agent is told what landed meanwhile.

## Rules
- Tools talk to the local daemon, not directly to the server, so there is one connection per worktree.
- Keep tool outputs short and actionable; they land in the agent's context.
- The hook never fails a tool and never blocks for long: starting a missing daemon is capped at about 3 s, and an unreachable daemon means silence.
