# daemon/ — the local replica

Owner: **Vazovski** (since 18 October 2026; built by the teammate through Phase 4). Keep `README.md` here, the guide for other teams, in step with the CLI (`src/index.ts`, `USAGE`).

## What this folder does
One process per worktree. It keeps the local folder in sync with the server's log and turns the agent's edits into commits. Design reference: the technical design doc (written when the project was called Agent Git), sections 6.3, 8 and 13.1.

## Responsibilities
1. Connect to `GET /stream` (WebSocket), send `{ "type": "subscribe", "fromLsn": <applied LSN> }`, apply entries strictly in LSN order; re-request on a gap.
2. Apply entries only at **safe points** (between agent tool calls, never during a test or build run). The Claude Code hook in `mcp/` signals them.
3. Use **Jujutsu colocated with git** (`jj git init --colocate`). The agent's unfinished work is jj's working-copy change `@`. To apply an entry: move `main` to it, then rebase `@` onto `main`. jj records conflicts instead of stopping; run Mergiraf on conflicted files and notify the agent only if something remains.
4. Compute read and write sets with the TypeScript compiler API (exact references), marking signature changes as `sigWriteSet`.
5. Send commits as `CommitRequest` (from `@pitstop/protocol`) with an idempotency key, retrying safely.

## Rules
- Every message matches `@pitstop/protocol`. Test against `packages/protocol/fixtures/` (see `src/index.test.ts`).
- Never delete or overwrite the agent's unfinished edits. If an apply fails, stop applying and report; jj's operation log can undo.
- Phase 0 spike first: confirm the exact jj command sequence for "move main, rebase @, detect conflicts" and write it down in this file.

## Phases owned here
1: stream + apply into a jj worktree + send commits. 2: read/write sets. 4: safe points, rebase of unfinished work, agent notifications.

For other teams, [README.md](README.md) in this folder is the user-facing guide: install, connect a repository, wire up Claude Code, the daily loop, refusals, limits, troubleshooting. Keep it in step with the CLI.

## Setup and the background daemon (the MVP path)
Users install the client from the server (`npm install -g https://<server>/pitstop-cli.tgz`, built by `packages/cli/`, which bundles this folder and `mcp/`), then run one command:
- `pitstop setup <server-url> <owner/name> [--token t] [--dir d] [--agent name]` (`setup.ts`): (a) `checkTools`: Node 22+, git and jj runnable (install hints per OS), jj's `user.name`/`user.email` (set with `jj config set --user` from `git config` when missing, else stop with the two commands); (b) `GET /repos/:owner/:name` with the token (404: create it on the website). A directory already configured for that repository and server (`--dir`, the cwd's git toplevel, the cwd, `./<name>`) is reused. An empty log imports the cwd's git checkout as `main` holds it (`init.ts` with `importFrom: "main"`), after these refusals: a checkout configured for another repository or server, or one that applied entries already (`init.ts` refuses the first too, `OtherCheckout`); no `main` with a commit (and, without `.jj`, a branch other than `main`); anything uncommitted (`git status --porcelain --untracked-files=all`, or `jj diff --from main --to @` when `.jj` exists; the wiring files do not count), since the log is append-only and jj would carry it into the agent's first commit. Then `.git/info/exclude` (only after those checks, and before jj's first snapshot), and `jj git init --colocate` when there is no `.jj` (`jj.ts` `jjInitColocated`: where git's `core.autocrlf` is `true`, or `core.eol` `crlf`, jj gets `working-copy.eol-conversion=input-output` from the first snapshot and in the repo config, `input` for `autocrlf=input`; otherwise jj 0.46 snapshots a Windows checkout's CRLF into `@`. In an existing `.jj` the setting is added and the changed files touched so jj re-reads them). A log with entries is cloned (`clone.ts`, whose `prepareWorktree` uses `jjInitColocated` too) into `--dir` or `./<name>`, never inside another checkout unless `--dir` says so. (c) `wire.ts`: `git ls-files` first, and a wiring file git tracks is the team's and left alone (for `.mcp.json`, the result names `claude mcp add --scope local pitstop -- …` and the CLI prints it as a to-do). Otherwise `.mcp.json` `{ command: "pitstop-mcp" }` (`cmd /c pitstop-mcp` with `NoDefaultCurrentDirectoryInExePath=1` on Windows: Claude Code starts MCP servers without a shell, npm's bin is a `.cmd` shim there, and cmd would otherwise prefer a `pitstop-mcp.cmd` in the checkout), the `pitstop-hook` PostToolUse hook, `enabledMcpjsonServers` and `mcp__pitstop` in `permissions.allow` (the owner chose on 18 October 2026 that the pitstop tools run without a prompt) in `.claude/settings.local.json` (Claude Code's per-user file; the team's `settings.json` is theirs, and Pitstop's hook is taken out of an untracked one an earlier version wrote), the house rules between markers in `CLAUDE.local.md`, all kept alongside what the files hold (hooks are filtered one by one: only `pitstop-hook` and `node "<abs>/mcp/dist/hook.js"` are Pitstop's), and exactly those three in `.git/info/exclude`; the agent's name goes into `.pitstop/config.json` (`agent`, under `PITSTOP_AGENT`). (d) `processes.ts` `startDaemon`, with the server, repository, token and agent setup was given in the daemon's environment; for a reused checkout whose server, token or agent changed, the running daemon is stopped first (it read them once). Errors that need the user are `SetupStopped` and print as one message, exit 1. The token is `--token` or `PITSTOP_TOKEN`, never the cwd's config.
- Every command but `setup`, `clone` and `init` acts on the nearest directory at or above the cwd with `.pitstop/config.json` (`config.ts` `findWorktree`, the same walk as mcp/src/autostart.ts); `start` and `daemon` refuse outside one. `start` gives the daemon the checkout's config over the shell (`config.ts` `daemonEnv`), and `configFrom` lets the token follow the server: the file's token goes to the file's server, and only `PITSTOP_TOKEN` to a different `PITSTOP_SERVER`.
- `pitstop start` / `pitstop stop` (`processes.ts`): the daemon detached (`detached`, `windowsHide`, stdio appended to `.pitstop/daemon.log`, `unref`), waited for until `/status` answers with the pid in `daemon.json`; `.pitstop/starting` keeps two starters from starting two. A daemon counts as running only when its pid lives and its API answers as that pid (a hard kill leaves a stale `daemon.json`, and the pid may be reused), so `stop` never signals a stranger. `pitstop daemon` refuses to start next to a running one.
- The agent side starts a missing daemon itself by running `pitstop start` (mcp/src/autostart.ts), so after a reboot opening Claude Code is enough.
- In the bundle, `index.ts`'s isMain check is off (`build-info.ts`, `BUNDLED`): the bundle's entry calls `runCli`. `daemonCommand()` runs the bundle file itself, or `index.js`/`index.ts` (with tsx's loader flags) next to `processes.ts`.

## Running it (Phases 1 and 2)
- `pitstop clone <server-url> <owner/name> [dir] [--token t]` makes a fresh worktree of a repository that is already on the server: it fetches the log and replays every entry through the apply sequence (`clone.ts`), so `main`, `@`, the config and the state end up where a long-running daemon would leave them, and two clones of one log agree on every commit id (the root commit is dated from the repository's creation). The server has no tree endpoint yet; a log of thousands of entries would want one.

In a worktree that is `jj git init --colocate`d with a `main` bookmark:
- `pitstop init <server-url> [--repo owner/name] [--token t]` once per worktree: writes `.pitstop/config.json` (the environment still overrides it: `PITSTOP_SERVER`, `PITSTOP_TOKEN`, `PITSTOP_REPO`), creates the repository on the server (`POST /repos`, idempotent), and, when that repository's log is empty and this worktree has applied nothing, imports the worktree as its first entry. A second worktree of the same repository is only configured; its daemon then receives the import from LSN 0. Once a repository is configured, subscribe, commits and intents carry it, and `GET /log` is asked for it.
- `pitstop import` by hand: every tracked text file as an add at base LSN 0, so the server can rebuild the tree at any entry (the type-check gate needs that).
- `pitstop daemon` (`npm run dev -w @pitstop/daemon -- daemon` from the repo) connects to `PITSTOP_SERVER` (default `http://localhost:8080`), subscribes from the LSN in `.pitstop/state.json`, applies entries in order and stops on the first failure. When it applies an entry over unfinished edits in `@`, it records the LSN those edits began at (`readBaseLsn` in the state file).
- `pitstop commit -m "<intent>"` sends `@` against `main` as a `CommitRequest` with file contents, the read and write sets from `symbols.ts` (empty when the worktree has no `tsconfig.json`), and `readBaseLsn` when the daemon recorded one. If the accepted entry is the next one for this worktree it is applied at once; otherwise the running daemon applies it in order.
- Environment: `PITSTOP_SERVER`, `PITSTOP_TOKEN`, `PITSTOP_REPO` (each wins over `.pitstop/config.json`, except that the file's token stays with the file's server), `PITSTOP_DEVELOPER`, `PITSTOP_AGENT`, `PITSTOP_DAEMON_PORT` (the local API's port; default a free one), and `PITSTOP_JJ_BIN` / `PITSTOP_GIT_BIN` / `PITSTOP_MERGIRAF_BIN` when the executables are not on PATH. `README.md` lists the same set for other teams.
- No server at hand: `npm run fake-server -w @pitstop/daemon` replays `packages/protocol/fixtures/server-messages.json` on port 8081 and accepts commits; with `PITSTOP_FAKE_LOG=empty` it starts with no entries, so an import becomes #1 as on a new server. The tests use the same fake (`src/fake-server.ts`); the ones against a real jj repo (`src/jj.test.ts`) skip themselves where jj is not installed.

Symbol sets (`symbols.ts`): two TypeScript programs from the worktree's own `tsconfig.json`, the tree at `main` and the tree at `@`, both in memory. A symbol is a top-level declaration or a class member, `path#qualified.name`. Write set: text changed, added or removed. Signature write set: the checker's signature or type string changed, or the symbol was removed. Read set: every project symbol a changed declaration refers to, types included, lib and `node_modules` excluded. A declaration's text excludes the comments above it, so a doc-comment-only edit is not a write; whitespace inside the declaration is. `src/symbols.test.ts` runs the two laptops' edits from `demo/scenario.md` against `demo/teamdb`.

## The agent side (Phase 4)
`pitstop daemon` also serves a local HTTP API on `127.0.0.1`, port in `.pitstop/daemon.json`, for the MCP tools and the hook in `mcp/` (`daemon.ts`; `local-client.ts` finds and calls it):
- `POST /safe-point`: the agent is between tools. Pending entries are applied now, and the answer carries notes for the agent: entries that changed symbols its change reads or writes (from `symbols.ts` on `@`), files it is editing that an entry touched, conflict markers an apply left, and the server's `warning`s for this agent since the last safe point. Once a safe point has been seen, entries wait for the next one; a daemon that has seen none for ten minutes applies as they arrive, as in Phase 1.
- `POST /intents {text, symbols?}`: opens a transaction on the server (`intents.ts`); the id goes into the state file, heartbeats carry it, the next commit closes it. Declaring also fixes `readBaseLsn` at the applied LSN of that moment.
- `POST /commit {intent}`: the same as the CLI; 200 with the changeset, or 409 with the server's rejection verbatim (`reason`, `message`, `conflictsWith`), which the commit tool shows the agent. A skew refusal (`escalated`, `repair_failed`) names the entries the agent read past and tells it to re-read them at head, so `commit.ts` moves `readBaseLsn` past those entries: the adapted commit is checked from there, not refused for the same skew again. The safe-point notes stay a heads-up only; they see the agent's edits, not what it read before editing, so they never move the read base. Found by the Phase 4 gate on 2026-10-17.
- `GET /status`, and from the server's query API (`brain.ts`): `GET /why?path=`, `GET /callers?symbol=` (readers from read sets, each with what it wrote, plus the writers; it says it is not a parsed call graph), `GET /history?symbol=`.
- `GET /presence`: who is working in the repository right now, `{ replica, ttlMs, entries }` (the live entries, this worktree's included, each with `ageMs`); the MCP `who` tool reads it.
- Presence (`presence.ts`, design doc 9.5): the brain's one CRDT, the last-writer-wins map from `packages/protocol/src/presence.ts`, never used for decisions. The worktree's replica id is `w_` + 8 hex, made once in `.pitstop/replica`; a `HybridClock` observes every stamp received, and the daemon merges every `presence` message into its copy of the document. It writes only its own entry: `working` with unfinished edits or an open intent, else `idle`; the open intent's id (state file) with its text and symbols (as declared, or from the server's `intent` messages); the paths of `@` against `main` (`Applier.changedPaths`, no file contents; under the worktree lock, at most every 5 s at safe points, fresh on declare and commit, and taken from the safe-point notes' own diff when entries were applied); `appliedLsn`. Published on `head` (the subscription is confirmed), at every safe point, after a declare and an accepted commit; a keepalive (same values, new stamp) with every heartbeat and 250 ms after applies; a tombstone on close. A safe point publishes in the background (the hook never waits on jj and git for presence; its overlap notes use the previous publish) and sends nothing when the values did not change and the last write is under 30 s old. When someone writes its key with a newer stamp it writes again only over a tombstone (the server's, for an old socket of ours that closed late), at most once per 5 s; a newer live entry means another process shares the replica id, which it logs once and does not answer (answering looped two daemons at tens of thousands of writes a second). Its copy of the document keeps at most 500 entries. Notes name at most 5 files and 5 symbols per overlap, then "and N more (call who for the full list)". Every entry is checked against the schema before it goes, since an invalid message costs the socket. At a safe point the notes add other live replicas (two-minute TTL) in the same files or symbols: `agent-b (lbala23) is also editing src/pages/ProfilePage.ts, for 'Show last-seen on the profile page'`, once per replica and file or symbol while the overlap lasts. A copied worktree copies `.pitstop/replica` too, like the state file: delete it in the copy.
- The brain (`brain.ts`, design doc section 9): `POST /intents` answers the server's intent plus `brief`, the brain in a few lines (version; at most ten accepted ADRs, those whose rules cover the declared symbols' files first, each as title, decision cut at 240 characters and its rules, an `ai_review` rule marked advisory; "+N more ADRs: call the brain tool"; live leases other agents hold on the declared symbols), from `GET /repos/:o/:n/brain`; an unreachable brain leaves `brief` empty and never fails the intent. `GET /brain` is the whole brain, one line per ADR, lease and open intent. `POST /lease {symbol, reason?, ttlSeconds?, release?}` takes a lease for the open intent in the state file, or releases this agent's own (naming its agent, developer and intent). With no open intent it answers `invalid` ("declare your intent first"): a lease lives and ends with an intent. The answer's `status` is `held`, `released`, `leased` (another agent holds it: the only one that means "leave it alone", and the only 409), `not_held` (nothing of yours to release) or `invalid` (the server's reason: a stale intent, a bad time to live…). A lease is held by its intent (`holdsLease`, as on the server), so the same person's other checkout counts as another agent. The daemon renews its own leases (`renewLeases`, every `leaseRenewMs`, default 20 s): once half a lease's time is gone it asks the server again, while the intent is open; the server renews nothing on a heartbeat. The stream client passes `brain` and `lease` messages on (`onBrain`, `onLease`), and the next safe point's notes carry an ADR accepted or superseded, leases other agents took or gave up on symbols this agent declared or in files it is editing (the last event per symbol), this agent's own lease ended without its asking (expired, or released while its intent is open), and its intent marked stale. Each event list keeps the last 100.
- Conflicts: the rebase writes git-style (diff3) markers (`--config ui.conflict-marker-style=git`). When Mergiraf is installed (`winget install Mergiraf.Mergiraf`, or `PITSTOP_MERGIRAF_BIN`), each conflicted file goes through `jj resolve --tool mergiraf <file>` (Mergiraf refuses `mergiraf solve` inside a jj repository); what structure allows (both sides added a key, a function, an import) is merged and reported as `resolved`, the rest keeps its markers and is reported to the agent at the next safe point.
- CLI: `pitstop intent -m "<text>" [-s a#b,c#d]` (prints the brain in brief), `pitstop safe-point` (the hook's command), `pitstop status`, `pitstop brain`, `pitstop lease <path#name> [-r why] [--release]` (the last two straight to the server, no daemon needed).

The daemon and `pitstop commit` are separate processes on one worktree, and the server pushes an accepted entry on the stream before it answers the commit, so both would apply the same entry at once. Every apply runs under `.pitstop/lock` (`state.ts`, `withWorktreeLock`) and re-reads the state once it holds the lock; the second one finds the entry applied. A lock older than a minute belongs to a dead process and is taken over. Found by the Phase 1 gate on 2026-10-17.

Source map: `stream.ts` (subscribe, order, gaps, readBaseLsn, holding for safe points), `daemon.ts` (the process: local API, safe points, notes), `presence.ts` (replica id, this worktree's presence, overlap notes), `intents.ts`, `brain.ts` (the brain and the query API from the server, and their lines for the agent), `jj.ts` (the apply sequence below, `@` as file changes, trees at `main` and `@`), `symbols.ts`, `commit.ts` (commit and import), `state.ts` (state file and lock), `config.ts`, `local-client.ts`, `fake-server.ts` (now also `POST /intents`, `GET /log`, scripted rejections, presence relayed, the brain, leases and the query API, `broadcast`), `setup.ts`, `wire.ts`, `processes.ts`, `build-info.ts`, `index.ts` (CLI).

## jj apply sequence
Tested on Windows 11 with jj 0.46.0 (`winget install jj-vcs.jj`) and git 2.x, in a colocated repo (`jj git init --colocate`), on 2026-10-17. The daemon runs these as child processes with the worktree as cwd; no shell is involved, so quote nothing.

The entry's commit is built with git plumbing, not by switching jj's working copy: the agent's files on disk are touched exactly once, by the final rebase.

```bash
# 0. Snapshot the agent's unfinished edits into @ and remember where to roll back to.
jj util snapshot
jj op log -n1 --no-graph -T id            # -> RESTORE_OP (128 hex chars)

# 1. Build the entry's commit on top of main. One blob per FileChange with content;
#    for a delete use `git update-index --force-remove <path>` instead of --cacheinfo.
git rev-parse refs/heads/main             # -> OLD_MAIN
git hash-object -w --stdin < <content>    # -> BLOB, one per file
GIT_INDEX_FILE=.git/pitstop-index git read-tree OLD_MAIN
GIT_INDEX_FILE=.git/pitstop-index git update-index --add --cacheinfo 100644,BLOB,<path>
GIT_INDEX_FILE=.git/pitstop-index git write-tree   # -> TREE; then delete .git/pitstop-index
git commit-tree TREE -p OLD_MAIN -m "#<lsn> <intent>"   # -> NEW_MAIN

# 2. Move main. The third argument is a compare-and-swap: fails if main moved underneath us.
git update-ref refs/heads/main NEW_MAIN OLD_MAIN

# 3. Rebase the agent's working copy @ onto the new main. jj imports git refs itself on every
#    command in a colocated repo, so `jj git import` is not needed (it prints "No import needed").
jj rebase -d main

# 4. Detect conflicts. The revset is `conflicts()`; `conflicted()` does not exist in 0.46.
jj log -r conflicts() --no-graph -T change_id   # empty output = clean; otherwise one change id per line
```

Observed results:
- Clean case (agent edited `b.txt`, entry changed `a.txt`): after step 3, `a.txt` has the entry's content, `b.txt` keeps the agent's edit, `@` sits on the new `main`.
- Conflict case (both changed the same line): step 3 still succeeds, `@` is marked `(conflict)`, step 4 prints its change id, and the file on disk carries jj's markers (`<<<<<<<`, `%%%%%%%`, `+++++++`, `>>>>>>>`). This is the input for Mergiraf (Phase 4).

Rollback, two levels:
- `jj undo` reverts only the rebase: `@` goes back onto the old main with the agent's edit intact and no markers, but `main` (jj bookmark and git ref) stays on the new entry.
- `jj op restore RESTORE_OP` reverts everything since step 0: `main` returns to OLD_MAIN in both jj and git, `@` is as snapshotted. Use this when an apply fails, then report; never retry over a half-applied state.

Windows 11 gotchas:
- jj stores index segments as 128-character file names under `.jj/repo/index/segments/`. Under a long worktree path (about 100 characters or more) `jj git init` fails with "The system cannot find the path specified (os error 3)". Keep worktrees short, like `C:\Users\<you>\Desktop\pitstop`. A `subst` drive letter does not help because jj canonicalizes the path.
- The jj identity must be set (`jj config set --user user.name/user.email`) or `@` is created with an empty author.
- Replacing `.pitstop/state.json` by rename fails with `EPERM` for a few milliseconds while another process (the daemon, the CLI, a test) still has it open for reading; `state.ts` retries both the read and the rename.
- When git made the repository's first commits (as `demo/scripts/reset.sh` does) and `jj git init --colocate` came after, git HEAD stays a symbolic ref to `main`. Step 2 would then move HEAD as well, and jj treats a moved HEAD as a `git checkout` the user already did, so step 3 leaves the files on disk untouched. The daemon detaches HEAD at its current commit before step 0 (`git update-ref --no-deref HEAD <commit>`), which jj does not notice. Found by the Phase 1 gate on 2026-10-17.
